# Reading a package miss and checking a fix

Availability, recognition, knowledge, reachability, application and production
capability are distinct questions. Locate the supported defect before
expanding a layer; more than one explanation may remain live.

## A good body cannot repair an unseen card

The selector sees the card before the body. A realistic request that does not
name the package shows whether its job is recognizable; compare it with
ordinary execution and with the nearest neighbor, not with a memorized pairing
of keyword and name. Truncation can hide the discriminator, which makes its
position matter. If the card sends the task to the wrong owner, body detail
cannot fix that first contact. Correct selection followed by poor results, on
the other hand, is no reason to rewrite the card.

When a routing question could change whether a package is created, kept,
merged or rewritten, look at first contact with only what the selector sees:
the name, the description as the listing shows it, and the neighbors' cards.
Use the smallest realistic prompts whose plausible outcomes lead to different
actions: a positive task that does not name the skill, a near-neighbor task, a
request that shares vocabulary but needs something else. If the choice from
the cards alone is wrong, repair the card or the boundary before adding body
detail.

Selection quality is measured over the right tasks: among tasks the package
should serve, how many select it rather than a neighbor, and how many tasks it
should not serve select it anyway. Raw invocation counts say nothing about
quality.

## Loaded knowledge can still be unhelpful

A usable artifact or decision shows benefit more directly than invocation
counts or adherence to headings. A package that repeats competence the model
already has consumes attention without adding knowledge; one that teaches a
wrong causal relationship produces fluent, systematic error.

A comparison with and without the skill can help attribute a difference to
the package when the task, model, base instructions, tools and help are held
fixed; sampling variation and the number and coverage of cases still limit
that inference. A
direct user correction that already names the missing distinction needs no
comparison. One representative result can reveal a defect; it does not
estimate reliability across a catalog.

## Depth has to be reachable when it is needed

A reference has value when the task can recognize its subproblem and reach the
resource before the choice it informs. Some models seldom open references from
the entrypoint, so a decisive rule kept only in a reference never reaches them;
move it into the body. If irrelevant depth is loaded routinely, the split does
not match real task boundaries. Not every resource belongs in every
occurrence; following the path of the actual task tells more than demanding
that every resource be read.

## Running the checks

Choose the check by the decision it serves. For selection, use requests that
do not name or paraphrase the skill. Add a named run only when it can
distinguish recognition from application, and keep its result separate from
the unassisted occurrence.
When deciding whether a package earns its place or which card to keep, run a
few realistic tasks and near-miss requests with and without the skill.

The available native creator or evaluator owns command syntax, input formats
and run records. Choose among its capabilities by what the decision needs:

- A with-skill comparison needs a stated baseline: no skill for whether to add
  one, the incumbent for whether a rewrite helps. Hold the rest of the task's
  conditions fixed and inspect the outputs side by side.
- A description comparison needs should-trigger and should-not-trigger
  requests, especially near-misses. Keep some requests outside the set used
  to tune the wording; a score on tuning cases overstates recognition elsewhere.
- A selection observation needs the actual invocation record. Little change
  in output quality does not prove that the skill was selected and ineffective;
  an occurrence that never loaded it cannot isolate its body's contribution.
- A fresh-agent trial gets a realistic request and the artifacts needed for
  the task, not the expected answer. Fresh context does not by itself remove
  shared instructions or establish an independent reviewer.
- A package validator checks source properties such as accepted frontmatter,
  naming and links. It cannot show selection, application or benefit.

The package decision needs the requests, what happened in each, and the
consequence; the tools keep the full runs.
